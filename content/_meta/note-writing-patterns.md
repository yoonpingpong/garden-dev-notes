## 개요

학습 노트를 처음 쓸 때 흔히 한 파일에 한 주제(예: "Value Object")의 모든 것을 우겨넣는다. 정의·비교·5가지 용도·예제·실수까지 다 한 파일에 모이면 어느 순간 600줄을 넘기고, 그 시점부터는 **본인조차 다시 읽기 싫어진다**.

줄 수가 임계치를 넘는 건 결과일 뿐이고, 실제 신호는 *"한 번에 읽고 머리에 들어오지 않는다"* 는 **reader fatigue**다.

이 노트의 1~12번 패턴은 `value-object.md` 한 파일이 그 임계를 넘어 [[../architecture/ddd/domain-behavior-in-vo|domain-behavior-in-vo]]·[[../architecture/ddd/immutability-benefits|immutability-benefits]] 두 자식 노트로 분리되는 과정에서 굳어졌다. 13~15번은 그 이후 "읽는 사람이 추측하지 않게 쓴다"는 기준으로 덧붙인 것이다. 코드 컨벤션이 아니라 **글쓰기 컨벤션**이다.

## 언제 적용하나

- 학습 노트 / 개념 정리 노트를 쓸 때 (코드 문서·API 레퍼런스가 아닌, 개인 지식 베이스용 글)
- 한 노트가 한 화면을 넘어가고 "다시 읽기 부담스럽다" 신호가 올 때
- ❌ bad case / ✅ good case 비교 패턴을 쓸 때
- Obsidian/Quartz 같은 양방향 링크 지원 vault에 노트를 누적할 때
- 공개 저장소(GitHub Pages 등)에 게시할 가능성이 있는 vault에서

> 빈 페이지에서 시작할 땐 `content/_meta/templates/learning-note.md` 템플릿을 `cp`하여 사용. 이 파일들의 15가지 패턴이 스켈레톤에 미리 박혀 있다.

## 15가지 작성 패턴

### 1. 분리 기준은 줄 수가 아니라 응집도

*"600줄 넘으면 자른다"* 가 아니다. 기준은:

> "이 단락이 자기만의 시나리오·코드·결론을 갖고 있어서 **혼자 떼어도 한 편의 글이 되는가**"

`value-object.md`의 5개 용도 중 3번(도메인 행위)·4번(불변성)만 풀 시나리오로 자식 노트가 된 이유 — 나머지 3개(타입 강제, 자가 검증, 컬렉션 키)는 본문 안에서 단락 한두 개로 충분히 설명되기 때문. 모든 항목을 균일하게 자르지 않는다. 자기 응집을 가진 단위만 떼어낸다.

### 2. 파일명은 예제가 아니라 주제

```
❌ money-as-vo.md            ← 사이드바에서 "Money?"
✅ domain-behavior-in-vo.md  ← "VO에 도메인 행위를 응집하는 이야기"
```

사이드바·검색·백링크 어디서 봐도 노트가 **다루는 개념**이 즉시 보여야 한다. 예제는 본문에 살고, 파일명은 *그 노트가 가리키는 개념*을 가리킨다.

### 3. 제목에서 부제를 빼라

```
❌ VO에 도메인 행위를 응집하기 — Money 예제
✅ VO에 도메인 행위를 응집하기
```

파일명이 이미 주제고, "Money 예제"라는 정보는 첫 문단을 읽으면 즉시 나온다. 제목은 **주제 한 마디**.

### 4. 헤딩 계층은 의미적 부모-자식

❌/✅ 케이스는 같은 시나리오의 두 변형이지 독립된 두 섹션이 아니다.

```
❌                            ✅
## ❌ 절차적 접근            ## 시나리오 — 주문 합계 계산
## ✅ VO 기반 접근              ### 요구사항
                                ### ❌ 절차적 접근
                                ### ✅ VO 기반 접근
                                ### 무엇이 좋아졌나
```

같은 부모(`## 시나리오`)를 공유하는 H3 형제는 *"이 둘은 비교 대상"* 이라는 신호를 **구조 자체로** 준다.

### 5. 헤딩에 설명 부제를 매달지 마라

```
❌ ### ❌ 절차적 접근 — 가격을 그냥 BigDecimal로
✅ ### ❌ 절차적 접근
```

헤딩 직후 첫 문단이 "가격을 단순 BigDecimal로 들고 다니면…"이라면 부제는 중복. **헤딩은 짧게, 설명은 본문에**.

### 6. 흔한 단어를 써라

```
❌ ## 요지   (한자어, 본문에서 잘 안 쓰는 단어)
✅ ## 개요   (즉시 인지되는 단어)
```

같은 자리에서 독자가 빠르게 인식하는 단어를 우선. 현학적 정확성보다 인지 속도.

기술 용어도 같은 원칙을 따른다. 번역하지 않고 현업에서 통용되는 표기를 그대로 쓴다.

```
❌ 경로 배정표, 하위망     ← 사전적으로는 맞지만 아무도 이렇게 부르지 않는다
✅ 라우팅 테이블, 서브넷
```

반대 방향도 마찬가지다. 한국어가 표준인 자리에 원어를 끼워 넣지 않는다.

```
❌ 이 노트는 캐시 인밸리데이션 스트래티지를 다룬다
✅ 이 노트는 캐시 무효화 전략을 다룬다
```

판단이 서지 않으면 기준은 하나다. 그 분야 개발자 둘이 대화할 때 입으로 나오는 쪽을 쓴다.

### 7. 코드 예제는 stdlib + 구체 데이터로 자족하게

가짜 의존성을 등장시키면 독자가 *"저게 뭐지?"* 하고 본문 흐름을 놓친다.

**의도만 표현하면 충분한 곳** — 주석 처리:
```java
public void issue(Address address) {
    address.setCity(address.getCity().toUpperCase());   // ⚠️ 원본 수정
    // 정규화된 address로 청구서를 인쇄한다 (이후 코드 생략)
}
```

**실패가 눈에 보여야 하는 곳** — 구체적 lookup:
```java
private static final Map<String, String> CITY_ZONES = Map.of(
    "Seoul", "ZONE-A",
    "Busan", "ZONE-B"
);

public void route(Address address) {
    String zone = CITY_ZONES.get(address.getCity());
    // address.getCity() == "SEOUL" → CITY_ZONES.get("SEOUL") → null
}
```

가상 객체(`deliveryRouter.lookup(...)`, `printInvoice(...)`)는 쓰지 않는다.

### 8. ❌/✅ 두 버전은 대칭으로

```
같은 데이터  (CITY_ZONES 맵 동일)
같은 호출 순서  (issue → route 동일)
같은 시나리오  (한 Address 공유)
유일한 차이  →  class Address (setter 있음)  vs  record Address (불변)
```

독자가 두 코드 블록을 옆에 놓고 비교할 때 **머릿속에서 토글할 변수가 정확히 하나**. 데이터·구조·문체까지 같으면 차이가 또렷이 드러난다.

### 9. 핵심 contrast는 구조까지 대칭

"도메인 언어로 읽힌다" 같은 핵심 비교 섹션은 다음 패턴으로:

```
### VO 버전
   코드 블록
   > 한국어 소리내어 읽기
   → 한 줄 결론

### 절차적 버전
   코드 블록
   > 한국어 소리내어 읽기
   → 한 줄 결론

### 핵심 차이
   - 불릿 1
   - 불릿 2
   - 불릿 3
```

끝의 결론을 **3개 불릿으로 분해** — 한 문단의 농밀한 문장보다 불릿이 스캐닝에 강하다.

### 10. 백링크는 양방향

A → B로 링크하면 B → A도 거는 게 기본값.

```
domain-behavior-in-vo ↔ value-object ↔ immutability-benefits
         ↕                  ↕                  ↕
         └──── record ↔ object-comparison ─────┘
```

Obsidian/Quartz 그래프 뷰의 가치는 **양방향 링크 밀도**에서 나온다. 단방향이면 6개월 뒤 "어디서 이걸 참조했더라" 검색에 실패한다.

### 11. publish 옵트인 + 보안 체크리스트

공개 vault는 `publish: true`를 명시적으로 켤 때만 노출. 체크리스트는:

- 비밀번호/토큰/API 키 없음
- DB 접속 정보 없음
- 내부 IP/도메인/호스트명 없음
- 회사 비공개 정보 없음
- 개인정보 없음
- 코드 예시는 placeholder

학습 노트라도 publish 게이트는 **맨 마지막 단계**. 자세한 룰은 [[../../CLAUDE]] 참조.

### 12. 반복 편집은 자연스러운 학습 방식

한 번에 완벽한 노트를 쓰지 않는다.

- 작은 편집을 많이 누적
- 주기적으로 한 발 물러나 통합/분리/리네이밍 결정
- 각 편집은 개별적으로 옳고, 누적된 결과가 **구조적 통찰**이 된다

`value-object.md` 분할도 한 번의 결정이 아니라 *"읽다 보니 지친다"* 라는 신호가 누적된 후 일어났다.

### 13. 간결함에도 하한선이 있다

패턴 1은 "길면 자른다" 방향으로 압력을 건다. 그 압력만 있으면 자르다가 정작 필요한 것까지 빠진다. 그래서 무엇을 줄여도 되고 무엇은 못 줄이는지 미리 갈라둔다.

줄여도 되는 것:

- 배경 설명, 역사적 맥락
- 같은 말의 재진술
- 안 써도 아는 당연한 문장
- 본문에서 한 번도 쓰지 않는 용어의 정의

줄이면 안 되는 것:

- 전제 조건 — 언제 성립하는 이야기인가
- 제약 사항 — 무엇이 불가능한가
- 예외 케이스 — 어디서 깨지는가
- 왜 그런가 — 동작만 적으면 6개월 뒤 응용이 안 된다

```
❌ 라우팅 테이블은 서브넷에 연결된다.
✅ 라우팅 테이블은 서브넷에 연결된다. 서브넷 하나당 정확히 하나이며,
   명시하지 않으면 메인 라우팅 테이블이 적용된다.
```

두 번째가 한 줄 더 길지만, 그 한 줄이 없으면 노트를 다시 열 이유가 사라진다. 제약과 예외는 분량이 아니라 노트의 존재 이유다.

### 14. 주어를 생략하지 마라

한국어는 주어를 흔히 생략하고, 대화에서는 그게 자연스럽다. 기술 문서에서는 오독의 1순위 원인이다.

```
❌ 삭제할 수 없다
✅ 로컬 라우트는 삭제할 수 없다

❌ 이것 때문에 통신이 안 된다
✅ 퍼블릭 IP가 없기 때문에 통신이 안 된다

❌ 설정이 반영되면 재시작된다
✅ 설정이 반영되면 워커 프로세스가 재시작된다
```

같이 지켜야 할 세 가지:

- 지시대명사(이것, 그것, 해당, 위의)는 가리키는 대상이 같은 문장 안에 없으면 쓰지 않는다
- 수동태로 행위 주체를 감추지 않는다. "처리된다"가 아니라 "누가 처리한다"
- 수식어가 어디에 걸리는지 애매하면 문장을 둘로 나눈다

검증 방법은 간단하다. 문단 하나를 앞뒤 맥락 없이 떼어놓고 읽었을 때 "무엇이?"라는 질문이 떠오르면 주어가 빠진 것이다.

### 15. 개념 하나에 예시 하나

새 개념을 설명한 직후에 예시를 붙인다. 예시 없이 개념만 둘 이상 연달아 나오면 그 지점이 독자가 이탈하는 자리다.

예시가 코드일 필요는 없다. 아래 넷 모두 예시다.

- 구체적인 수치 — "느리다"가 아니라 "200ms에서 3초로"
- 실패하는 상황 — 이 규칙을 어겼을 때 실제로 무엇이 깨지는가
- 실제 설정값 — 옵션 이름만이 아니라 실제로 넣는 값
- 익숙한 대상에 빗댄 비유 — 단, 비유는 개념을 대체하지 않고 뒤따라온다

코드로 쓸 때의 규칙은 패턴 7을 따른다. 비유를 쓸 때는 어디까지 성립하는 비유인지 한 줄로 못 박는다. 경계를 안 적은 비유는 나중에 잘못된 추론의 근거가 된다.

## 왜 이게 중요한가

- **본인이 다시 안 읽는 노트는 zero value.** 응집도 기반 분리 + 주제 기반 파일명은 미래의 본인이 6개월 뒤 사이드바에서 클릭할 확률을 높인다.
- **글의 구조가 곧 사고의 구조.** 헤딩 계층을 의미적 부모-자식으로 맞추면 글을 쓰면서 *"이 둘은 진짜 비교 가능한가?"* 가 강제로 검증된다.
- **대칭은 인지 부하를 줄인다.** 가변 vs 불변, 절차적 vs VO 같은 contrast는 다른 모든 변수를 묶어둘 때만 신호가 분리된다.
- **양방향 백링크는 지식 그래프의 산소.** 한 방향만 있으면 그래프 뷰에서 단절된 노드처럼 보인다.
- **publish 옵트인은 일관된 보안 백스톱.** *"당연히 시크릿 없겠지"* 가정 대신 명시적 체크.

## 사례 — value-object 노트 분할

### Before

`value-object.md` 한 파일에 정의·Entity 비교·5가지 용도·각 용도별 풀 예제·실수·record 섹션까지 **600+줄**. 본인조차 *"다시 읽기 부담스럽다"* 는 신호가 옴.

### After

부모 노트는 5가지 용도를 *개관 + 짧은 코드 스니펫*으로만 유지. 풀 시나리오가 필요한 두 용도만 자식 노트로 분리:

```
content/architecture/ddd/
├── value-object.md                  ← 부모 (정의 + 5용도 개관)  ~370줄
├── domain-behavior-in-vo.md         ← 3번 용도 풀 시나리오       ~150줄
└── immutability-benefits.md         ← 4번 용도 풀 시나리오       ~200줄
```

분리 기준은 줄 수가 아니라 *"각자 한 편의 글이 되는가"*. 나머지 3개 용도(타입 강제, 자가 검증, 컬렉션 키)는 본문 단락만으로 충분해서 분리하지 않음.

### 파일명 진화

```
money-as-vo.md                 →  domain-behavior-in-vo.md
address-as-vo.md               →  immutability-benefits.md
```

*"Money/Address 예제"* 가 아니라 *"VO에 행위를 응집한다 / VO 불변성의 이점"* — 노트가 다루는 **개념**을 파일명에.

### 헤딩 재구조화

```
Before:                          After:
## ❌ 절차적 접근                ## 시나리오 — 주문 합계 계산
## ✅ VO 기반 접근                  ### 요구사항
                                    ### ❌ 절차적 접근
                                    ### ✅ VO 기반 접근
                                    ### 무엇이 좋아졌나
                                    ### 도메인 언어로 읽힌다는 것
```

두 케이스가 시나리오의 형제로 묶이며 *"이 둘은 비교 대상"* 이라는 구조적 신호 발생.

### 코드 예제 정제

```java
// Before — 가짜 의존성
public void route(Address address) {
    String zone = deliveryRouter.lookup(address);  // deliveryRouter?
    printInvoice(address);                          // printInvoice?
}

// After — stdlib + 구체적 데이터
private static final Map<String, String> CITY_ZONES = Map.of(
    "Seoul", "ZONE-A", "Busan", "ZONE-B"
);
public void route(Address address) {
    String zone = CITY_ZONES.get(address.getCity());
    // → null → 매핑 실패, 라우팅 불가
}
```

가짜 객체 0개. lookup 실패가 주석으로 가시화.
