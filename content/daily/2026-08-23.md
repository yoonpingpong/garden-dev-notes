## 확인하고 노트에 반영한 것

Spring Data 소스·레퍼런스로 확인:

- `default-page-size` 20 / `max-page-size` 2000, `size < 1`이면 예외가 아니라 기본값으로 폴백
- `one-indexed-parameters`는 요청 파싱에서 1을 뺄 뿐이라 응답 `number`는 0부터
- `sort` 파싱은 마지막 토큰만 `ignorecase` → 방향 순으로 보고 나머지 전부를 프로퍼티로 처리
- `Window<T>`·`ScrollPosition` = Spring Data 3.1, `PagedModel` = 3.3
- Hibernate 컬렉션 fetch 경고: 6은 `HHH90003004`, 5는 `HHH000104`

## 노트에서 뺀 것 — 코드로 확인한 뒤 다시 넣을 것

문서로 확인이 안 돼서 일단 노트에서 제거했다. 실제로 돌려보고 결과가 맞으면 되돌린다.

### 1. `@EntityGraph` + `Sort` 파라미터 (원래 `pageable.md`의 2단계 조회 권장안)

```java
@EntityGraph(attributePaths = "items")
List<Order> findByIdIn(List<Long> ids, Sort sort);
```

```java
List<Order> orders = repo.findByIdIn(ids.getContent(), pageable.getSort());
```

확인할 것:

- 생성된 SQL에 `order by`가 붙는가 (`@EntityGraph`가 만드는 조인과 함께여도)
- 컬렉션 fetch + `Sort`만 있을 때(페이징 없음) `HHH90003004` 경고가 안 뜨는가
- 같은 메서드에 `Pageable`과 `Sort`를 같이 두면 `IllegalStateException`이 나는가 (문서에는 그렇게 적혀 있으나 미확인)

동적 정렬을 두 쿼리에 일관되게 전달하는 가장 깔끔한 방법이라 확인되면 되돌릴 값이 있다. 현재 노트는 JPQL `order by` + 메모리 재정렬 두 가지만 남겨 뒀다.

### 2. `Limit` 파라미터 (원래 `keyset-pagination.md`)

`repo.findNextPage(..., Limit.of(10))` 형태. 현재 노트는 `PageRequest.of(0, 10)`으로 바꿔 뒀다.

확인할 것: `@Query` 메서드의 파라미터로 `Limit`을 받을 수 있는가, 어느 버전부터인가.

### 3. 커서 쿼리의 실제 동작 (`keyset-pagination.md`의 핵심 주장)

논리는 확실하지만 실행 결과를 본 적은 없다. `created_at`이 같은 행을 15건쯤 만들어 두고 끝까지 순회하면서 확인할 것:

- 중복·누락이 없는가
- `or` 절을 빼면 실제로 같은 `created_at` 행들이 통째로 건너뛰어지는가
- 실행 계획이 `(status, created_at, id)` 인덱스를 타는가

### 4. 노트에서 뺀 미확인 표준 동작

문서로 개별 확인하지 않아 `pageable.md`에서 제거했다. 대부분 오래된 표준 동작이라 사실일 가능성이 높지만, 확인 전까지는 노트에 두지 않는다.

- `Slice`가 `size + 1`을 조회해 다음 페이지 유무를 판단한다는 구현 방식 (문서에는 "다음 Slice가 있는지만 안다"까지만 확인됨)
- 없는 프로퍼티로 정렬하면 `PropertyReferenceException`이 난다
- `@PageableDefault(size, sort, direction)`로 메서드별 기본값을 바꾼다
- `@Query(countQuery = ...)`로 count 쿼리를 따로 지정한다
- `Page.map()`이 페이징 정보를 유지한 채 내용만 변환한다
- 커서 방식에서 `(a,b) < (?,?)` 행 값 비교의 JPQL/HQL 지원 범위 — HQL은 지원하나 `<`/`>`는 방언에 따라 갈린다(Oracle·SQL Server·DB2 등 false)는 것까지만 확인. `keyset-pagination.md`에서는 "방언에 따라 갈린다"로만 서술하고 펼쳐 쓰는 형태를 남겼다
