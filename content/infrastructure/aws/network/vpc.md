## 개요

VPC를 한 문장으로 설명하면 이렇다.

> AWS 계정 안에 내가 IP 대역을 직접 정해서 만드는, 논리적으로 격리된 가상 네트워크 경계

VPC는 네트워크 구성의 최상위 경계다. 그 아래를 서브넷이 가용 영역 단위로 나누고, 보안 그룹은 다시 ENI 단위로 적용된다. 자세한 계층은 [계층 구조](#계층-구조)에서 다룬다.

온프렘에 빗대면 서버 한 대가 아니라 팀이 통째로 할당받은 사설망 한 블록에 해당한다. 다만 이 비유는 주소 체계와 격리 범위에만 적용된다. 물리적으로 전용 장비를 받는 것은 아니다. [격리는 논리적이다](#격리는-논리적이다)에서 다시 다룬다.

## VPC를 만들면 생기는 것

VPC를 생성하면 다음 세 가지가 자동으로 함께 만들어진다.

- 메인 라우팅 테이블 — 로컬 라우트 한 줄이 미리 들어 있다
- 기본 네트워크 ACL — 인바운드와 아웃바운드 모두 허용 상태
- 기본 보안 그룹 — 같은 보안 그룹 내부 통신만 허용

반대로 다음은 생기지 않는다. 직접 만들어야 한다.

- 서브넷
- 인터넷 게이트웨이
- NAT Gateway

이 구분이 헷갈리는 이유는 두 가지 예외 때문이다. 계정을 만들면 리전마다 딸려 오는 기본 VPC에는 가용 영역별 서브넷이 이미 들어 있다. 그리고 콘솔에서 "VPC 등"(VPC and more) 옵션으로 만들면 마법사가 서브넷, NAT Gateway, 라우팅 테이블까지 한 번에 만들어 준다. 두 경우 모두 VPC 생성이 곧 서브넷 생성인 것처럼 보이지만, 실제로는 마법사가 대신 여러 API를 호출한 것이다.

## 소유와 연결

VPC와 하위 리소스의 관계는 두 가지로 나눠 봐야 한다. 이 둘을 섞으면 라우팅 테이블이 어디에 붙는 것인지 헷갈린다.

소유 관계는 VPC가 리소스를 가지는 것이다. 라우팅 테이블, 네트워크 ACL, 보안 그룹, 서브넷은 만들 때 VPC가 정해지고 이후 바꿀 수 없다. 다른 VPC로 옮기려면 새로 만들고 기존 것을 지우는 방법뿐이다.

연결 관계는 서브넷과 라우팅 테이블 사이에 맺어진다. AWS는 이것을 association이라고 부르고 별도로 관리한다.

```
VPC (10.0.0.0/16)
├── 라우팅 테이블 A (메인)      ← VPC 생성 시 자동
├── 라우팅 테이블 B (직접 생성)
├── 서브넷 1 (10.0.1.0/24) ──연결──> 라우팅 테이블 B
├── 서브넷 2 (10.0.2.0/24) ──연결──> 라우팅 테이블 B
└── 서브넷 3 (10.0.3.0/24) ──연결 없음──> 메인(A)이 적용
```

정리하면 라우팅 테이블은 VPC에 속해서 태어나고, 서브넷과 연결되어 동작한다. 서브넷 3처럼 명시적 연결이 없으면 메인 라우팅 테이블이 암묵적으로 적용된다.

여기서 자주 나오는 오해가 하나 있다. 서브넷을 만들어도 그 서브넷의 CIDR이 라우팅 테이블에 추가되지는 않는다. 라우팅 테이블에 들어가는 것은 VPC CIDR 하나뿐이고, 서브넷 대역은 이미 그 안에 포함되어 있으니 로컬 라우트 한 줄이 전부 처리한다.

## 계층 구조

```
VPC          리전 단위. 여러 가용 영역에 걸친다
 └ 서브넷     가용 영역 하나에 묶인다. 다른 가용 영역으로 옮길 수 없다
    └ ENI     인스턴스나 Lambda 등에 붙는 네트워크 인터페이스. 보안 그룹이 여기 적용된다
```

서브넷이 가용 영역에 묶인다는 점이 실무 구성을 결정한다. 멀티 AZ 구성이란 결국 가용 영역 수만큼 서브넷을 만드는 일이다. RDS의 서브넷 그룹이나 ELB가 최소 두 개 가용 영역의 서브넷을 요구하는 것도 같은 이유다.

## 시나리오 — CIDR을 좁게 잡았을 때

### 요구사항

- 서비스 초기에는 퍼블릭 서브넷 2개, 프라이빗 서브넷 2개로 시작한다
- 1년 뒤 ECS를 도입하면서 서브넷을 4개 더 추가해야 한다
- ECS는 awsvpc 모드로 동작하므로 태스크마다 ENI가 하나씩 붙는다

### ❌ 10.0.0.0/24로 시작

필요한 IP가 많지 않아 보여서 /24로 잡은 경우다.

```
VPC CIDR: 10.0.0.0/24        주소 256개 (32 - 24 = 8비트, 2^8)

10.0.0.0/26    퍼블릭 1      64개
10.0.0.64/26   퍼블릭 2      64개
10.0.0.128/26  프라이빗 1    64개
10.0.0.192/26  프라이빗 2    64개
                             ← 남은 대역 0
```

1년 뒤 서브넷을 추가하려 하면 남은 대역이 없다. 그런데 VPC CIDR은 축소도 안 되지만 기존 대역을 확장하는 것도 안 된다. 10.0.0.0/24를 10.0.0.0/16으로 넓히는 조작 자체가 존재하지 않는다.

할 수 있는 것은 보조 CIDR을 추가하는 것뿐이다.

```
기본 CIDR:  10.0.0.0/24
보조 CIDR:  10.1.0.0/16      ← 연속되지 않은 별개 블록
```

동작은 한다. 다만 이 VPC의 주소 공간은 이제 두 조각이다. 온프렘이나 다른 VPC와 연결할 때 두 대역을 각각 광고하고 각각 라우팅해야 하고, 방화벽 정책도 두 줄이 된다. 조각이 늘어날수록 관리 부담이 커진다. 요금이 더 나오지는 않는다. 사설 주소 공간은 과금 대상이 아니다.

### ✅ 10.0.0.0/16으로 시작

같은 서브넷 요구사항을 /16 안에서 배치한 경우다.

```
VPC CIDR: 10.0.0.0/16        주소 65,536개 (32 - 16 = 16비트, 2^16)

10.0.0.0/24    퍼블릭 1      256개
10.0.1.0/24    퍼블릭 2      256개
10.0.16.0/24   프라이빗 1    256개
10.0.17.0/24   프라이빗 2    256개
                             ← 10.0.2.0 이후, 10.0.18.0 이후 전부 여유
```

1년 뒤 서브넷 4개를 추가할 때 남은 대역에서 그대로 잘라 쓰면 된다. 주소 공간은 여전히 한 덩어리다.

퍼블릭을 10.0.0부터, 프라이빗을 10.0.16부터 시작한 것은 용도별로 대역 블록을 예약해 두기 위해서다. 각각 /20 블록 하나씩을 차지한다.

```
10.0.0.0/20     퍼블릭 블록      10.0.0.0  ~ 10.0.15.255   (/24 자리 16개)
10.0.16.0/20    프라이빗 블록    10.0.16.0 ~ 10.0.31.255   (/24 자리 16개)
10.0.32.0 이후  미사용
```

같은 용도의 서브넷을 블록 안에서 15개까지 이어 붙일 수 있고, 방화벽 정책이나 라우팅에서 서브넷을 하나씩 나열하는 대신 10.0.16.0/20처럼 블록 하나로 표현할 수 있다.

블록 경계는 십진수가 아니라 2의 거듭제곱을 따른다. /20 블록은 세 번째 옥텟이 0, 16, 32, 48에서 시작한다. 프라이빗 시작점을 10.0.10.0으로 잡으면 이 요약이 성립하지 않는다. 10.0.10.0/20은 실제로 10.0.0.0/20으로 해석되어 퍼블릭 서브넷까지 함께 포함해 버린다.

### 무엇이 달랐나

| | ❌ /24로 시작 | ✅ /16으로 시작 |
|---|---|---|
| 초기 요구 충족 | 충족 | 충족 |
| 서브넷 추가 여지 | 없음 | 충분 |
| 확장 방법 | 보조 CIDR 추가만 가능 | 남은 대역에서 분할 |
| 주소 공간 | 두 조각으로 분리 | 한 덩어리 유지 |

두 구성의 차이는 처음에 적은 프리픽스 하나뿐이다. VPC의 사설 대역은 실제로 소비되는 자원이 아니므로 좁게 잡아서 얻는 이득이 없다. 겹치지 않는 선에서 넉넉히 잡는 것이 기본이다.

## 격리는 논리적이다

VPC는 나만 쓰는 전용 장비를 받는 것이 아니다. 같은 물리 서버와 네트워크 장비 위에 여러 고객의 VPC가 함께 올라가 있고, AWS가 패킷마다 어느 VPC 것인지 표시를 붙여 서로 섞이지 않게 한다.

사무실에 비유하면 독채를 임대한 것이 아니라 공유 오피스의 한 구역을 받은 것에 가깝다. 문은 잠기고 남이 들어올 수 없지만 건물과 전기는 함께 쓴다. 이 비유는 분리 방식에만 적용된다. 규제상 물리적 분리가 필요하다면 Dedicated Host 같은 별도 옵션을 써야 한다.

격리는 초기 상태일 뿐 고정된 성질도 아니다. 필요하면 다음 수단으로 연결한다.

- VPC 피어링 — VPC 두 개를 직접 연결
- Transit Gateway — 여러 VPC와 온프렘을 허브 하나로 연결
- VPC 엔드포인트 — S3나 DynamoDB에 인터넷을 거치지 않고 접근
- Site-to-Site VPN, Direct Connect — 온프렘과 연결

피어링에는 제약이 하나 있다. A와 B를 연결하고 B와 C를 연결해도 A에서 C로는 가지 못한다. 중간을 경유하는 경로가 만들어지지 않기 때문이다.

```
VPC-A ──피어링── VPC-B ──피어링── VPC-C

A → B  가능
B → C  가능
A → C  불가
```

그래서 VPC가 세 개를 넘어가면 피어링을 그물처럼 거는 대신 Transit Gateway로 묶는다.

여기서 [라우팅 테이블 노트](vpc-route-table.md)의 로컬 라우트 우선 규칙이 제약으로 돌아온다. 피어링으로 연결하려는 두 VPC의 대역이 겹치면 로컬 라우트가 먼저 잡아채기 때문에 연결 자체가 성립하지 않는다. 나중에 연결할 가능성이 있는 VPC끼리는 처음부터 대역을 겹치지 않게 설계해야 한다.

## 기본 VPC

계정을 만들면 리전마다 기본 VPC가 하나씩 생긴다. 새 리전을 활성화할 때도 같다.

### 왜 존재하나

EC2-Classic 시절과의 하위 호환 때문이다.

2013년 이전에는 인스턴스를 띄우면 AWS가 관리하는 공용 네트워크에 바로 놓였고, 사용자는 네트워크를 몰라도 됐다. RunInstances API에 AMI와 인스턴스 타입만 넘기면 끝이었다.

VPC 모델로 전환하면서 인스턴스는 반드시 특정 서브넷에 속해야 하게 됐다. 그대로 두면 서브넷 ID 없이 호출하던 기존 스크립트와 도구가 전부 깨진다. 그래서 AWS는 "지정하지 않으면 여기로 간다"는 기본값을 만들었고 그것이 기본 VPC와 기본 서브넷이다. EC2-Classic은 2022년에 종료됐지만 기본 VPC는 남았다.

부수적으로는 진입 장벽을 낮추는 효과가 있다. 계정을 처음 만든 사람이 인스턴스 하나 띄우려고 VPC, 서브넷, 인터넷 게이트웨이, 라우팅 테이블을 순서대로 이해해야 한다면 대부분 중도에 이탈한다.

### 구성

- CIDR은 172.31.0.0/16 고정
- 가용 영역마다 /20 서브넷 하나씩
- 인터넷 게이트웨이 연결
- 메인 라우팅 테이블에 0.0.0.0/0 → 인터넷 게이트웨이
- 모든 서브넷의 퍼블릭 IP 자동 할당이 켜져 있음

마지막 두 항목이 중요하다. 기본 VPC에는 프라이빗 서브넷이 하나도 없다. 인스턴스를 띄우면 자동으로 퍼블릭 IP가 붙고 인터넷에서 도달 가능한 상태가 된다.

### 실무에서 걸리는 부분

프로덕션에는 맞지 않는다. 모든 서브넷이 퍼블릭이라 데이터베이스나 내부 서비스를 둘 자리가 없다. 편의를 위해 만들어진 것이지 안전한 기본값으로 설계된 것이 아니다.

CIDR이 172.31.0.0/16으로 고정이라는 점도 문제가 된다. 계정을 여러 개 쓰다가 나중에 피어링이나 Transit Gateway로 묶으려 하면 전부 같은 대역이라 연결할 수 없다. 계정이 늘어난 뒤에 발견하면 되돌리기 어렵다.

실수로 사용하기도 쉽다. 서브넷을 지정하지 않으면 조용히 기본 VPC로 들어간다. 프로덕션 VPC에 띄웠다고 생각한 인스턴스가 기본 VPC의 퍼블릭 서브넷에 있는 경우가 실제로 나온다.

그래서 조직 차원에서는 계정 생성 직후 전 리전의 기본 VPC를 삭제하는 것이 표준에 가깝다. 삭제 후 다시 필요하면 `create-default-vpc`로 만들 수 있다.
